\begin{abstract}
Large language model (LLM) query expansion is typically applied either
unconditionally or not at all, despite well-documented evidence that
unconditional expansion is net-harmful on a non-trivial fraction of
queries. We formulate query expansion instead as a bounded, observable
agentic decision, and evaluate it under a train/validation/test
discipline strict enough to survive review: every retrieval-config
choice, verifier-model selection, and recovery threshold is fixed on a
held-out TripClick TAIL \emph{validation} split before a single frozen
touch of the \emph{test} split, per research question. We study three
questions: (RQ1) can qrel-free telemetry predict whether an expansion
will help or hurt; (RQ2) does a closed-loop agent conditioned on that
telemetry outperform an otherwise identical static, failure-conditioned
expansion pipeline; and (RQ3) can observability-driven recovery detect
and correct deliberately injected failures. A first pass at this study
used an under-tuned BM25 baseline (nDCG@10 $0.228$, well below the
$0.267$ literature reference for this split); correcting it --- stemming
plus title-field weighting, selected entirely on validation ---
raises BM25 to nDCG@10 $0.315$, \emph{above} the reference point, and
changes every downstream conclusion. On the frozen test set, the
selected verifier (nothing beat a plain hand-picked baseline on
validation, so we deploy the honestly-fit model anyway) generalizes
better than its own noisy validation estimate suggested: Pearson
$r=0.114$ ($p<0.001$), ROC-AUC $0.552$, against click-derived
relevance labels never seen during selection. Neither static expansion
nor the closed-loop agent significantly outperforms corrected BM25
(static: $+0.0007$, agent: $+0.0009$ nDCG@10, both 95\% CI crossing
zero), nor does the agent beat static ($+0.0002$). Critically, this is
not because no headroom exists: a retrospective oracle with perfect
per-query accept/reject knowledge would gain $+0.0246$ nDCG@10 over
BM25 ($p<0.001$) --- roughly $30\times$ what the deployed verifier
actually captures --- showing the failure mode is a weak
\emph{detector}, not an absent \emph{opportunity}. Fault-injection
recovery is fault-type-dependent: a content-level entity-injection
fault is not significantly aided (mean nDCG@10 change $+0.0081$,
$95\%$ CI crossing zero) despite near-perfect detection recall, a
grounding-corruption fault is significantly recovered ($+0.0099$), and
a system-level reranker fault is never detected at all (recall
$0.000$) because the selected verifier's fitted weights place
essentially no mass on reranker-derived features --- the same
structural gap RQ1 identifies, now visible in a concrete failure mode.
We report a real implementation defect found mid-study and its
correction as part of the record, since fixing it materially changed
prior results. Taken together, these findings map where
observability-guided control earns its keep and where it does not,
under a protocol designed so that map is trustworthy.
\end{abstract}

\section{Introduction}

Large language models can generate useful pseudo-documents, alternative
phrasings, and disambiguating context for a search query
\cite{query2doc,mugi}, and corpus-grounded generation --- conditioning
the rewrite on retrieved evidence rather than the query text alone ---
improves on naive query-only rewriting. Existing work has established
that LLM query expansion \emph{can} help. It has not established when an
operational system should trust an expansion enough to use it. In
practice, expansion is applied unconditionally to every query or not at
all; neither policy is safe, since unconditional rewriting is reliably
net-harmful on a measurable fraction of queries, particularly
underspecified or already-well-served ones.

We treat this as a control problem rather than a generation problem.
Borrowing the observe-diagnose-act-recover discipline of site reliability
engineering \cite{sre-slo} and the trace/metric vocabulary of
OpenTelemetry \cite{opentelemetry,otel-semconv}, we build an agent whose
action space is a small set of interpretable, corpus-grounded expansion
operators, whose control loop alternates actions with structured
observations in the manner of ReAct \cite{react}, and whose accept,
roll-back, replan, and abstain decisions are driven by runtime telemetry
rather than the language model's own self-assessment. The central
question is not whether an LLM can produce a useful expansion --- that
is established --- but whether \emph{runtime observability} can make
expansion selective, recoverable, and cost-aware. This paper reports
what we found rigorously answering that question, including where the
answer was no, as a necessary complement to the mostly-positive existing
literature.

\subsection{Research Questions}

\textbf{RQ1 (Detection).} Can qrel-free retrieval and agent-runtime
telemetry identify unhealthy retrieval states and predict whether query
expansion is likely to help or harm, without access to relevance
judgments at inference time?

\textbf{RQ2 (Control).} Does an agent that conditions expansion actions
on that telemetry outperform an otherwise identical \emph{static},
failure-conditioned expansion pipeline --- the same retriever, grounding
mechanism, generator, and fusion method, differing only in whether a
closed control loop can observe an action's consequences and recover
from a bad one?

\textbf{RQ3 (Recovery).} After a harmful rewrite or a simulated
system-level fault, can observability-driven verification detect the
degradation and select an appropriate recovery action to restore
retrieval quality, under a bounded action budget --- and does this hold
even for a verifier whose general-purpose detection power (RQ1) is only
weakly informative?

\subsection{Contributions}

We contribute (1) an agent architecture treating LLM query expansion as
a bounded, typed-tool action inside a closed observability loop, with a
telemetry model and failure taxonomy behind it; (2) a frozen
train/validation/test protocol (Section~\ref{sec:protocol}) under which
every retrieval-config, verifier-selection, and threshold decision is
made on held-out validation before one single-touch test evaluation, so
RQ1--RQ3 report generalization results, not in-sample
characterizations; (3) a corrected BM25 baseline, selected entirely on
validation, that moves our TripClick TAIL retriever from below to above
the published reference point and changes every downstream conclusion;
(4) a full-scale, frozen-test evaluation of the closed-loop agent
against a matched static comparator, plus a retrospective oracle
analysis separating ``no control opportunity exists'' from ``the
opportunity exists but our detector cannot exploit it''; (5) a
fault-injection recovery study showing which failure types a
qrel-free verifier can and cannot recover from, tied back to which
telemetry features it actually weights; and (6) an honest account of a
real implementation defect, discovered and corrected mid-study.

\section{Related Work}

\textbf{LLM query expansion.} Query2doc \cite{query2doc} generates
pseudo-documents from an LLM and appends them to the query. MuGI
\cite{mugi} generates and fuses multiple expansions. Both treat
expansion as an unconditional, one-shot generation step; neither
conditions expansion on retrieval-state telemetry nor recovers from a
harmful rewrite once issued.

\textbf{Agentic control loops.} ReAct \cite{react} interleaves
reasoning with actions and observations, the template for our
observe-act-observe structure, but at a much smaller, more measurable
action space: a fixed set of typed retrieval operators rather than
free-form tool calls, keeping the policy interpretable and letting a
lightweight, non-LLM controller drive it.

\textbf{Observability and reliability engineering.} OpenTelemetry's
trace/metric/log separation and GenAI semantic conventions
\cite{opentelemetry,otel-semconv} supply a naming discipline for our
telemetry. Google's SRE framing of a Service Level Objective as a
target range, not a single metric to optimize \cite{sre-slo}, motivates
our Agent Search SLO: maximize quality subject to harm, cost, and
latency constraints frozen \emph{before} evaluation.

\textbf{Benchmarks.} TripClick \cite{tripclick} has genuine
head/torso/tail query-frequency structure, unlike benchmarks that treat
``hard'' as a synonym for low-BM25-score. MS MARCO Chameleons
\cite{ms-marco-chameleons} isolates queries resistant to reformulation;
TREC DL 2019 \cite{trec-dl-2019} supplies deep NIST judgments; BEIR's
NFCorpus \cite{beir} is used here only for engineering iteration.

\section{System Design}

\subsection{Agent State and Control Loop}

The agent's state at step $t$ is $s_t = (q_0, q_t, R_t, O_t, H_t, B_t)$,
where $q_0$ is the immutable original query, $q_t$ the active search
expression, $R_t$ the current ranking, $O_t$ the observability state,
$H_t$ the episode's action/observation history, and $B_t$ the remaining
action budget. The control loop is
\[
\begin{aligned}
\footnotesize
\textsc{Observe} &\to \textsc{Diagnose} \to \textsc{Act} \to \textsc{Retrieve} \\
&\to \textsc{Observe} \to \textsc{Verify} \\
&\to \{\textsc{Accept}, \textsc{Rollback}, \textsc{Replan}, \textsc{Stop}\}.
\end{aligned}
\]
The critical property this loop is built to test is that the second
decision (accept/rollback/replan/stop) depends on evidence the agent's
own first action created --- as opposed to a static pipeline that
receives the same query, initial ranking, evidence, generator, and
verifier, but executes exactly one predetermined route. Isolating this
dependency, not simply comparing against unmodified BM25, is the
paper's central experimental contrast (Section~\ref{sec:rq2}).

The action space is deliberately small and interpretable:
\[
\begin{aligned}
\footnotesize
A = \{&\textsc{NoExpand}, \textsc{Vocabulary}, \textsc{Context}, \textsc{Ambiguity}, \\
&\textsc{EntityNormalize}, \textsc{Rollback}, \textsc{Replan}, \textsc{Stop}\}.
\end{aligned}
\]
\textsc{Vocabulary} maps informal user
language onto corpus-compatible terminology; \textsc{Context} adds a
corpus-supported missing facet to an underspecified query;
\textsc{Ambiguity} disambiguates toward the interpretation the evidence
best supports; \textsc{EntityNormalize} resolves aliases, abbreviations,
and canonical-name mismatches. The LLM is invoked through exactly one
typed tool, \texttt{generate\_expansion(action, query, evidence)}; it
is never the sole arbiter of whether its own output is used. That
judgment is made by a separate, non-generative controller
(Section~\ref{sec:controller}).

\subsection{Observability Model}
\label{sec:observability}

Every query episode produces one trace with spans
\texttt{retrieve\_original} $\to$ \texttt{build\_evidence} $\to$
\texttt{plan\_action} $\to$ \texttt{generate\_expansion} $\to$
\texttt{retrieve\_expanded} $\to$ \texttt{rerank} $\to$ \texttt{verify}
$\to$ \texttt{recover\_or\_accept} $\to$ \texttt{fuse}. The observation
vector $O_t$ spans three telemetry families. \emph{Retrieval telemetry}:
top score, score margin, normalized score entropy, query-term coverage,
mean rare-term IDF, entity overlap, top-$k$ ranking overlap against the
previous state, reranker/BM25 disagreement, lexical result coherence,
and ranking stability under a small controlled query perturbation.
\emph{Agent telemetry}: selected operator, trajectory length, previous
verifier score, rewrite-to-original semantic drift, introduced entities,
repeated actions, and remaining budget. \emph{System telemetry}:
per-tool latency, token counts, and tool errors or timeouts. Every
feature here is computable without relevance judgments, which is what
makes the resulting verifier usable at inference time.

\subsection{Failure Taxonomy}

We label episodes into ten failure categories (vocabulary mismatch,
underspecification, ambiguity, entity mismatch, intent drift,
confirmation bias, retriever disagreement, tool degradation, budget
exhaustion, healthy retrieval), each with an observable telemetry
signature and preferred recovery action, giving the observability layer
something concrete to predict rather than treating it as post hoc
dashboards; this directly motivates Section~\ref{sec:rq3}'s
fault-injection protocol.

\subsection{Verifier and Controller}
\label{sec:controller}

The verifier, \texttt{verify(previous\_state, new\_state)}, produces a
scalar judgment of whether an action's consequences look like an
improvement, using telemetry alone. Rather than hand-picking its
weights, we calibrate them against click-derived qrels (Section~\ref{sec:setup}):
for a sample of episodes, we execute one expansion action, compute the
true nDCG@10 change of the resulting ranking against those labels, and
fit the verifier's weights to predict that change from the telemetry
features described in Section~\ref{sec:observability}. Click labels are
available only during this offline calibration; the deployed verifier
never sees one. We treat this fitted model as an
artifact --- trained by a dedicated script and loaded at inference time
--- rather than a set of constants transcribed from a one-off
calibration run, so that recalibration is a script re-run, not a source
edit. The recovery controller is a small deterministic finite-state
machine: below a calibrated harmful threshold the agent rolls back to
the pre-action ranking; above a calibrated accept threshold it fuses the
new ranking in via reciprocal-rank fusion; in between it replans with an
untried operator, subject to a hard cap of two model calls per query.
Both thresholds are calibrated empirically (Section~\ref{sec:setup}), not
guessed.

\section{Experimental Setup}
\label{sec:setup}

\subsection{Datasets}

TripClick \cite{tripclick} is the primary benchmark: 1{,}523{,}878
documents, split evenly across head/torso/tail frequency buckets, each
further split into train/validation/test (1{,}175 queries per split per
bucket) --- the only candidate dataset reflecting genuine observed
query-frequency structure rather than treating ``tail'' as a synonym
for ``hard for BM25.'' All results concern the TAIL split. Labels are
click-derived, not human-assessed (binary raw clicks, matching the
label type this split's published reference point uses
\cite{tripclick}); we use ``qrel'' and ``click label'' interchangeably,
neither implying editorial judgment. NFCorpus \cite{beir} (3{,}633
documents, 323 queries) was used only for engineering iteration.

\subsection{Experimental Protocol}
\label{sec:protocol}

A first pass at this study calibrated the verifier and thresholds on
the same episodes later used to report RQ1--RQ3 --- an in-sample
characterization a reviewer could correctly read as overstating
generalization. We froze a stricter protocol instead, in a committed
config rather than left implicit: TAIL \emph{validation} may be used
for any retrieval-config, verifier, or threshold decision; TAIL
\emph{test} may be touched at most once per research question, purely
for evaluation, after every upstream decision is frozen, with no
decision afterward conditioned on a test-set outcome. This discipline
directly produced the paper's first finding, below.

\subsection{A Corrected Retrieval Baseline}
\label{sec:bm25-fix}

BM25 over an unstemmed FTS5 index scored nDCG@10 $0.228$ on TAIL test
--- $15\%$ below the $0.267$ reference reported for this exact split
and label type \cite{tripclick-strong-baselines}. Selecting entirely on
validation (never test), we found two config choices that close this
gap: Porter stemming (val nDCG@10 $0.235 \to 0.270$) and weighting the
title field ten times body weight in a title/body-split FTS5 index (val
nDCG@10 climbing to a clear plateau at that ratio, $0.327$, MRR peaking
there and declining beyond it). A single, one-time sanity check of the
frozen config against the withheld test set --- not a selection
criterion --- gives nDCG@10 $0.315$, \emph{above} the published
reference. We report this because an under-tuned baseline mechanically
inflates the apparent value of anything compared against it: every
downstream conclusion in this paper (Sections~\ref{sec:rq2}--\ref{sec:rq3})
changed once this fix was in place, and we regard resolving it as a
precondition for the rest of the study rather than an implementation
footnote.

\subsection{Implementation}

Sparse retrieval uses BM25 over a SQLite FTS5 index \cite{sqlite-fts5}
rather than a JVM Lucene index, forced by a JVM crash under Pyserini
\cite{pyserini} on our target hardware; two further lessons surfaced at
this corpus's scale, both silent-corruption risks in the same category
as Section~\ref{sec:bm25-fix}'s baseline gap and
Section~\ref{sec:defect}'s telemetry defect: FTS5's default MATCH
combining operator is \emph{conjunctive} (silently required every
multi-term query's terms to co-occur, collapsing recall without an
error), and FTS5 indexes only the \texttt{MATCH} column (a companion
lookup, e.g.\ document identifier, degrades to a full table scan ---
invisible at small scale, catastrophic at $1.5$M rows, an $18\times$
slowdown until a companion indexed table was added). Cross-encoder
reranking (\texttt{cross-encoder/ms-marco-MiniLM-L6-v2}
\cite{minilm-cross-encoder}) is applied to the top 100 BM25 candidates,
reranking the top 50. Generation uses a locally hosted, 4-bit quantized
2--3B-parameter model with a hard cap of two calls per query episode and
a 32--64 token structured output, so the language model is never the
entire decision surface, only one typed tool within it.

\subsection{Verifier Calibration Methodology}
\label{sec:calib-method}

Following Section~\ref{sec:protocol}, we collect calibration episodes
(one expansion action per query, true nDCG@10 change against click
labels) on TAIL \emph{validation} ($n=1147$--$1168$ depending on
feature family), and compare three feature families against two model
classes each, to characterize the detection ceiling rather than accept
the first plausible fit: (i) six retrieval-telemetry deltas; (ii) the
same six plus four reranker- and length-derived features; and (iii)
family (ii) plus three dense-embedding features. We compare a
fixed-weight baseline, a 5-fold cross-validated linear fit, and a
5-fold cross-validated GBDT fit, on each family, against true nDCG@10
change under Pearson correlation (Table~\ref{tab:rq1}) --- this
selects a model, and is never itself reported as evidence the signal
generalizes (Section~\ref{sec:rq1} reports that separately, from one
frozen touch of test). Recovery thresholds are calibrated the same
way, by checking which candidate score cutoffs on validation actually
separate true-harmed episodes from the rest.

\subsection{Metrics}

Retrieval quality is nDCG@10, Recall@100, and MRR, plus the fraction of
queries helped/unchanged/harmed relative to a baseline. For the
recovery study (Section~\ref{sec:rq3}) we report Detection Recall
$P(\text{intervened}\mid\text{harmful})$, False Alarm Rate
$P(\text{intervened}\mid\text{healthy})$, and recovery gain in mean
nDCG@10 with vs.\ without recovery on identically corrupted episodes.
We additionally report a retrospective \emph{oracle ceiling}: per
query, $\max(\text{baseline}, \text{treatment})$ under true click
labels --- the outcome a perfect, non-deployable, qrel-\emph{using}
selective policy would achieve, diagnosing whether headroom exists
independent of whether our qrel-free verifier can find it
(Section~\ref{sec:rq2}). Significance is via paired bootstrap
(10{,}000 resamples) throughout.

The frozen model generalizes better than its noisy validation estimate
suggested: $r=0.114$ on test is small but real ($p<0.001$, $R^2\approx

no-skill baselines (Figure~\ref{fig:roc-pr}). We read the val/test gap

larger test set landing positive does not retroactively make the
selection procedure sound --- it means this particular frozen artifact
happens to generalize, which we could not have known before freezing
it. \textbf{RQ1's answer}: qrel-free telemetry carries a real but weak
detection signal that survives out-of-sample evaluation, but that
signal was never distinguishable from noise on the data used to select
it.

\subsection{Is There Any Headroom at All?}
\label{sec:oracle}

A null result here is ambiguous: either no meaningful control
opportunity exists on this corpus, or one exists but this verifier
cannot find it. We resolve this with a retrospective oracle
(Section~\ref{sec:setup}): per query, take whichever of BM25 or the
treatment ranking true click labels say is better. This oracle is not
deployable --- it uses labels unavailable at inference time --- and
exists purely to bound the second explanation.

\section{RQ3: Which Failures Are Recoverable?}
\label{sec:rq3}

RQ1 and RQ2 leave open whether observability has \emph{any} practical
value, or whether a weak general detector is simply useless. We test a
narrower claim: that the same weak verifier can still serve as a
safety net against \emph{large, obvious} failures even though it
cannot reliably judge \emph{subtle, natural} ones. We inject three
fault types at their natural point of corruption --- an unsupported
entity appended to the expansion, a grounding passage swapped for a
non-supporting one, and the reranker disabled --- and compare, on
identical corrupted episodes, an always-accept ablation against the
real calibrated controller.

\subsection{A Defect That Changed the Answer}
\label{sec:defect}

An early pass at this study found the reranker-disabled fault
essentially undetectable (recall $0.185$) while the other two looked
strong. Tracing this revealed a real defect: the reranked ranking was
computed, at real latency cost, and fed into telemetry, but never
actually applied to the ranking the agent accepted or evaluated ---
disabling the reranker was mechanically a no-op regardless of verifier
quality. Fixing it exposed a second, subtler defect it was
entangled with: the verifier's telemetry was still computed from the
pre-rerank ranking, judging a different top-$k$ than the one being
accepted. We corrected both --- the reranked top-$k$ now leads the
accepted ranking, and telemetry is reordered to match it before
scoring --- and re-ran calibration to confirm the deployed verifier and
its thresholds did not need retraining on the corrected telemetry
(corrected-pipeline Pearson $r=0.146$ vs.\ the original $0.134$; a
fresh refit did not clear the bar to replace it). We report this
defect in full, not as a footnote, because a component computed purely
for observability is architecturally easy to leave disconnected from
the outcome it explains, and that disconnection produces results that
look coherent --- in this case, unrealistically strong --- until
someone investigates why an otherwise well-motivated intervention
shows no effect.

The three fault types split into three distinct outcomes, each with a
different explanation, so ``is recovery useful'' has no single answer
--- only a per-failure-type one. \textbf{Entity injection} is
detected almost every time (recall $0.974$) but flagged almost
indiscriminately (false alarm $0.939$): the controller treats nearly
any entity-injected rewrite as suspect whether or not the injection
was actually benign, and rolling back that many healthy episodes
offsets the genuine catches, leaving a positive but not significant
net effect. \textbf{Grounding corruption} is the one clean recovery
success ($+0.0099$, $p<0.05$): moderate recall ($0.528$) paired with a
comparable false alarm rate ($0.469$) is discriminating enough, on
this fault type specifically, to produce a real net gain. \textbf{Reranker
disabled} is never detected at all (recall $0.000$): the selected
verifier's fitted weights (Section~\ref{sec:calib-method}) place
essentially zero mass on reranker-derived features (\texttt{reranker\_top\_score}
$+0.0007$, \texttt{reranker\_score\_margin} $+0.0007$, against
\texttt{coverage\_gain} $+0.2051$ and \texttt{disagreement}
$-0.2528$), so a fault that manipulates reranker behavior specifically
is structurally invisible to it --- the same feature-weighting profile
selected purely from RQ1's validation-set model search, now surfacing
as a concrete blind spot rather than an abstract correlation ceiling.

\textbf{RQ3's answer is that recoverability is fault-specific, not a
property of the verifier in general}: content-level corruption is
recoverable when the verifier's telemetry is discriminating for that
specific corruption pattern (grounding), a wash when it is not
(entity injection, blunt detection swamped by false alarms), and a
system-level fault is entirely unrecoverable when it manipulates a
component the verifier's fitted weights do not track at all
(reranker). This traces directly back to RQ1: a verifier is not
uniformly weak or strong across failure types, it is weak or strong
\emph{per feature the failure happens to perturb}.

\section{Discussion}

Read together under the frozen protocol, RQ1--RQ3 and the oracle
analysis sketch one coherent finding rather than four independent
ones. RQ1's detection signal is weak but real out-of-sample
($r=0.114$ on test, despite a validation estimate indistinguishable
from noise): not zero, not strong. RQ2 shows that a closed control
loop built on that signal adds nothing over a matched static pipeline
on a properly-tuned retrieval baseline. The oracle analysis
(Section~\ref{sec:oracle}) is what turns those two facts into a
diagnosis rather than a shrug: real, large control headroom exists
($+0.0246$ nDCG@10 available to a perfect selector) and the deployed
verifier captures almost none of it, so the bottleneck is
\emph{specifically} detection quality, not an absent opportunity or a
control-loop design flaw. RQ3 sharpens this further by showing
detection quality is not one number but a per-feature property: the
verifier recovers a fault type when its fitted weights happen to track
the features that fault perturbs (grounding corruption), and is
structurally blind to a fault type when they do not (reranker
disabled, weights near zero on every reranker-derived feature). A weak
overall correlation is therefore not just an aggregate ceiling; it
decomposes into specific, predictable blind spots that a practitioner
could in principle inspect \emph{before} deployment by asking which
features a candidate fault would perturb and whether the fitted
verifier weights those features at all.

Two things here were found only by refusing a convenient result: the
BM25 baseline (Section~\ref{sec:bm25-fix}) looked adequate until
checked against a published reference, reversing RQ2's conclusion
entirely; the reranker-wiring defect (Section~\ref{sec:defect}) looked
like a strong recovery result until one fault type's implausible
near-zero effect prompted investigation. Both are cases where a
component --- a retrieval baseline, an observability signal --- is
architecturally easy to leave unchecked against an external reference,
and the resulting error looks coherent rather than broken. A frozen protocol
with a mandatory external sanity check (Section~\ref{sec:protocol})
structurally defends against the first; the second we only found by
distrusting a result that seemed too good, which no protocol
automates.

\section{Limitations}
\label{sec:limitations}

The oracle ceiling (Section~\ref{sec:oracle}) is retrospective and uses
test-set click labels directly --- a valid upper-bound diagnostic,
never a deployable method. The generator is a locally hosted, quantized
2--3B parameter model under a strict two-call budget; we do not know
whether a larger or API-hosted generator would change RQ1's ceiling or
RQ2's null result. All results concern TripClick's TAIL split; HEAD,
TORSO, MS MARCO Chameleons, and TREC DL 2019/2020 are left to future
work. Click-derived qrels are an imperfect relevance proxy inherited
from the benchmark, not introduced by our protocol. The corrected
baseline's title-weight ratio ($10\times$ body) was selected on a
genuine validation-set plateau, not cherry-picked, but we have not
tested whether it transfers beyond TripClick's title-informative
health-literature abstracts. RQ3's ``per-feature blind spot''
explanation is a plausible mechanism consistent with the observed
pattern, not one we verified with faults targeting other feature
subsets.

\section{Conclusion}

We evaluated a closed-loop, observability-guided query-expansion agent
under a train/validation/test discipline strict enough to survive the
scrutiny that sank an earlier, leakier pass at this same study ---
which itself surfaced the paper's first finding: an honestly-selected
BM25 baseline fix inverted every downstream conclusion. On the
corrected baseline, the agent does not outperform static expansion,
and neither outperforms BM25; but the oracle analysis shows this is a
detection failure, not an absent opportunity, and the recovery study
shows that failure is a per-feature property, not a uniform ceiling.
We report both defects found by refusing a convenient result as part
of this record, in the belief that the discipline required to catch
them is worth more to this line of research than a single flattering
number would have been.
