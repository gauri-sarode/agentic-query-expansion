\begin{abstract}
Large language model (LLM) query expansion is typically applied either
unconditionally or not at all, despite well-documented evidence that
unconditional expansion is net-harmful on a non-trivial fraction of
queries. We formulate query expansion instead as a bounded, observable
agentic decision, evaluated under a strictly separated
validation/test protocol: every retrieval-config, verifier-model, and
threshold decision is fixed on a held-out TripClick TAIL
\emph{validation} split before a single frozen touch of \emph{test},
per research question. A first pass used an under-tuned BM25 baseline
(nDCG@10 $0.228$, below the $0.267$ literature reference); correcting
it --- stemming plus title-field weighting, chosen entirely on
validation --- raises BM25 to $0.315$, above the reference, and
changes every downstream conclusion. Telemetry available before any
action predicts whether unexpanded retrieval is already poor with
ROC-AUC $0.649$ on frozen test, but the same telemetry vocabulary is
markedly worse at the harder, actionable question --- will a
\emph{specific} expansion help this query --- at ROC-AUC only $0.552$
($r=0.114$, $p<0.001$). Detection is not actionability, and that gap
is this paper's central finding. Consistent with it, neither static
expansion nor a closed-loop agent significantly outperforms corrected
BM25 (static: $+0.0007$, agent: $+0.0009$ nDCG@10, CIs crossing zero),
nor does the agent beat static ($+0.0002$); reranking alone, with no
expansion, significantly \emph{hurts} ($-0.0302$, $p<0.001$), so
expansion's role here is largely offsetting harm the reranker
introduces. This is not for lack of headroom: an oracle with perfect
per-query knowledge gains $+0.0246$ nDCG@10 over BM25 ($p<0.001$), of
which the verifier captures only $2$--$13\%$ across intervention
budgets. Fault-injection recovery is fault-specific and, via a causal
feature-perturbation analysis, mechanistically explained: a
grounding-corruption fault is significantly recovered ($+0.0099$), an
entity-injection fault is detected almost every time but flagged
almost indiscriminately (net effect not significant), and a
reranker-disabling fault is never recovered (recall $0.000$) because
the fault \emph{increases} the verifier's healthy-state score rather
than merely evading weak features. Generalization is worse still
outside the calibration split: action-utility AUC falls to $0.148$
(HEAD) and $0.214$ (TORSO), both below chance. We report a real
implementation defect found mid-study and its correction. Runtime
observability reliably detects retrieval failure, but the stronger
property autonomous recovery needs --- predicting whether a specific
intervention will help --- is not delivered by the same telemetry,
under a protocol designed so that finding is trustworthy.
\end{abstract}

\section{Introduction}

Large language models can generate useful pseudo-documents, alternative
phrasings, and disambiguating context for a search query
\cite{query2doc,mugi}, and corpus-grounded generation --- conditioning
the rewrite on retrieved evidence rather than the query text alone ---
improves on naive query-only rewriting. Existing work establishes that
LLM query expansion \emph{can} help, not when an operational system
should trust an expansion enough to use it. In practice, expansion is
applied unconditionally or not at all; neither is safe, since
unconditional rewriting is reliably net-harmful on a measurable
fraction of queries, particularly underspecified or already-well-served
ones.

We treat this as a control problem rather than a generation problem.
Borrowing the observe-diagnose-act-recover discipline of site
reliability engineering \cite{sre-slo} and the trace/metric vocabulary
of OpenTelemetry \cite{opentelemetry,otel-semconv}, we build an agent
whose action space is a small set of interpretable, corpus-grounded
expansion operators, whose control loop alternates actions with
structured observations as in ReAct \cite{react}, and whose accept,
roll-back, replan, and abstain decisions are driven by runtime
telemetry rather than the language model's own self-assessment. The
central question is not whether an LLM can produce a useful
expansion --- that is established --- but whether \emph{runtime
observability} can make expansion selective, recoverable, and
cost-aware. Answering it surfaces a distinction the selective query
expansion and query performance prediction literature has not, to our
knowledge, isolated: predicting that retrieval is failing and
predicting that a specific intervention will fix it are different
tasks, and telemetry good at the first can be useless at the second.
This paper reports what we found, including where the answer was no.

\subsection{Research Questions}

\textbf{RQ1 (Detection vs.\ Actionability).} Can qrel-free retrieval
and agent-runtime telemetry (a) identify that unexpanded retrieval is
already unhealthy, and (b) predict whether a \emph{specific} expansion
action is likely to help or harm --- and, if both are possible, is the
second any easier than the first once the first is solved?

\textbf{RQ2 (Control).} Does an agent that conditions expansion actions
on that telemetry outperform an otherwise identical \emph{static},
failure-conditioned expansion pipeline --- the same retriever, grounding
mechanism, generator, and fusion method, differing only in whether a
closed control loop can observe an action's consequences and recover
from a bad one?

\textbf{RQ3 (Recovery).} After a harmful rewrite or a simulated
system-level fault, can observability-driven verification detect the
degradation and select an appropriate recovery action to restore
retrieval quality, under a bounded action budget --- and does this hold
even for a verifier whose general-purpose detection power (RQ1) is only
weakly informative?

\subsection{Contributions}

We contribute (1) an agent architecture treating LLM query expansion as
a bounded, typed-tool action inside a closed observability loop, under
a frozen train/validation/test protocol (Section~\ref{sec:protocol})
where every retrieval-config, verifier, and threshold decision is made
on validation before one single-touch test evaluation; (2) a corrected
BM25 baseline, selected entirely on validation, moving our TripClick
TAIL retriever above the published reference and changing every
downstream conclusion; (3) a direct comparison, from one telemetry
vocabulary, of failure-\emph{detection} against
intervention-\emph{utility} prediction, showing these differ and only
the first is reliable; (4) a frozen-test evaluation of the closed-loop
agent against a matched static comparator, with an oracle and
selectivity-frontier analysis quantifying captured headroom; (5) a
fault-injection study with a causal feature-perturbation analysis
explaining, not just reporting, which faults a qrel-free verifier
recovers, plus a cross-split check showing that ranking degrades below
chance outside its calibration split; and (6) an honest
account of a real implementation defect, found and corrected mid-study.

\section{Related Work}

\textbf{LLM query expansion.} Query2doc \cite{query2doc} generates
pseudo-documents from an LLM and appends them to the query; MuGI
\cite{mugi} generates and fuses multiple expansions. Both treat
expansion as unconditional, one-shot generation, conditioning on
neither retrieval-state telemetry nor a harmful rewrite's recovery.

\textbf{Agentic control loops.} ReAct \cite{react} interleaves
reasoning with actions and observations, the template for our
observe-act-observe structure, but with a much smaller action space:
typed retrieval operators rather than free-form tool calls, keeping
the policy interpretable under a non-LLM controller.

\textbf{Observability and reliability engineering.} OpenTelemetry's
trace/metric/log separation and GenAI semantic conventions
\cite{opentelemetry,otel-semconv} supply a naming discipline for our
telemetry. Google's SRE framing of an SLO as a target range, not a
metric to optimize \cite{sre-slo}, motivates our Agent Search SLO:
maximize quality subject to harm, cost, and latency frozen
\emph{before} evaluation.

\textbf{Query performance prediction and selective expansion.} Classic
query performance prediction \cite{qpp-clarity} and selective query
expansion \cite{selective-qe} already ask whether a query is hard, or
likely to benefit from expansion, from retrieval signal alone. We
split that into two predictive targets sharing one telemetry
vocabulary --- is retrieval failing, versus will \emph{this} action
fix it --- and show qrel-free telemetry answers the first far better
(Section~\ref{sec:rq1}).

\textbf{Benchmarks.} TripClick \cite{tripclick} has genuine
head/torso/tail query-frequency structure, unlike benchmarks that treat
``hard'' as a synonym for low-BM25-score, which is why it is our sole
evaluation corpus.

\section{System Design}

\subsection{Agent State and Control Loop}

The agent's state at step $t$ is $s_t = (q_0, q_t, R_t, O_t, H_t, B_t)$,
where $q_0$ is the immutable original query, $q_t$ the active search
expression, $R_t$ the current ranking, $O_t$ the observability state,
$H_t$ the episode's action/observation history, and $B_t$ the remaining
action budget. The control loop is $\textsc{Observe} \to
\textsc{Diagnose} \to \textsc{Act} \to \textsc{Retrieve} \to
\textsc{Observe} \to \textsc{Verify} \to \{\textsc{Accept},
\textsc{Rollback}, \textsc{Replan}, \textsc{Stop}\}$. The critical property this loop is built to test is that the second
decision (accept/rollback/replan/stop) depends on evidence the agent's
own first action created --- as opposed to a static pipeline that
receives the same query, initial ranking, evidence, generator, and
verifier, but executes exactly one predetermined route. Isolating this
dependency, not simply comparing against unmodified BM25, is the
paper's central experimental contrast (Section~\ref{sec:rq2}).

The action space is deliberately small and interpretable: $A=\{$
\textsc{NoExpand}, \textsc{Vocabulary}, \textsc{Context},
\textsc{Ambiguity}, \textsc{EntityNormalize}, \textsc{Rollback},
\textsc{Replan}, \textsc{Stop} $\}$.
\textsc{Vocabulary} maps informal user language onto
corpus-compatible terminology; \textsc{Context} adds a corpus-supported
missing facet to an underspecified query; \textsc{Ambiguity}
disambiguates toward the interpretation the evidence best supports;
\textsc{EntityNormalize} resolves aliases, abbreviations, and
canonical-name mismatches. The LLM is invoked through exactly one typed
tool, \texttt{generate\_expansion(action, query, evidence)}; it is
never the sole arbiter of its own output's use --- that judgment is a
separate, non-generative controller's (Section~\ref{sec:controller}).

\subsection{Observability Model}
\label{sec:observability}

Every query episode produces one trace with spans
\texttt{retrieve\_original} $\to$ \texttt{build\_evidence} $\to$
\texttt{plan\_action} $\to$ \texttt{generate\_expansion} $\to$
\texttt{retrieve\_expanded} $\to$ \texttt{rerank} $\to$ \texttt{verify}
$\to$ \texttt{recover\_or\_accept} $\to$ \texttt{fuse}. $O_t$ spans
three telemetry families. \emph{Retrieval}: top score, score margin,
normalized score entropy, query-term coverage, mean rare-term IDF,
entity overlap, top-$k$ ranking overlap against the previous state,
reranker/BM25 disagreement, lexical result coherence, and ranking
stability under a small controlled query perturbation. \emph{Agent}:
selected operator, trajectory length, previous verifier score,
rewrite-to-original semantic drift, introduced entities, repeated
actions, remaining budget. \emph{System}: per-tool latency, token
counts, tool errors/timeouts. Every feature is computable without
relevance judgments, which is what makes the verifier usable at
inference time.

\subsection{Failure Taxonomy}

We label episodes into ten failure categories (vocabulary mismatch,
underspecification, ambiguity, entity mismatch, intent drift,
confirmation bias, retriever disagreement, tool degradation, budget
exhaustion, healthy retrieval), each with an observable telemetry
signature and preferred recovery action, motivating
Section~\ref{sec:rq3}'s fault-injection protocol.

\subsection{Verifier and Controller}
\label{sec:controller}

The verifier, \texttt{verify(previous\_state, new\_state)}, produces a
scalar judgment of whether an action's consequences look like an
improvement, using telemetry alone. Rather than hand-picking its
weights, we calibrate them against click-derived qrels
(Section~\ref{sec:setup}): for a sample of episodes, we execute one
expansion action, compute the true nDCG@10 change against those
labels, and fit the verifier's weights to predict that change from the
telemetry features of Section~\ref{sec:observability}. Click labels
are available only during this offline calibration; the deployed
verifier never sees one, and is treated as an artifact --- trained by
a dedicated script, loaded at inference time --- so recalibration is a
script re-run, not a source edit. The recovery controller is a small
deterministic finite-state machine: below a calibrated harmful
threshold the agent rolls back to the pre-action ranking; above a
calibrated accept threshold it fuses the new ranking via
reciprocal-rank fusion; in between it replans with an untried operator,
capped at two model calls per query. Both thresholds are calibrated
empirically (Section~\ref{sec:setup}), not guessed.

\section{Experimental Setup}
\label{sec:setup}

\subsection{Datasets}

TripClick \cite{tripclick} is the primary benchmark: 1{,}523{,}878
documents, split evenly across head/torso/tail frequency buckets, each
further split into train/validation/test (1{,}175 queries per split
per bucket). All results concern the TAIL split unless stated
otherwise (Section~\ref{sec:robustness}). Labels are click-derived,
not human-assessed (binary raw clicks, matching the label type this
split's published reference point uses \cite{tripclick}); we use
``qrel'' and ``click label'' interchangeably, neither implying
editorial judgment.

\subsection{Experimental Protocol}
\label{sec:protocol}

A first pass at this study calibrated the verifier and thresholds on
the same episodes later used to report RQ1--RQ3 --- an in-sample
characterization unsuited to an out-of-sample generalization claim. We
froze a stricter protocol instead, in a committed config rather than
left implicit: TAIL \emph{validation} may be used for any
retrieval-config, verifier, or threshold decision; TAIL \emph{test} may
be touched at most once per research question, purely for evaluation,
after every upstream decision is frozen, with no decision afterward
conditioned on a test-set outcome. This discipline directly produced
the paper's first finding, below.

\subsection{A Corrected Retrieval Baseline}
\label{sec:bm25-fix}

BM25 over an unstemmed FTS5 index scored nDCG@10 $0.228$ on TAIL test
--- $15\%$ below the $0.267$ reference for this exact split and label
type \cite{tripclick-strong-baselines}. Selecting entirely on
validation, we found two config choices that close this gap: Porter
stemming (val nDCG@10 $0.235 \to 0.270$) and weighting the title field
ten times body weight in a title/body-split FTS5 index (val nDCG@10
climbing to a clear plateau at that ratio, $0.327$, MRR peaking there
and declining beyond it). A single, one-time sanity check of the frozen
config against withheld test --- not a selection criterion --- gives
nDCG@10 $0.315$, \emph{above} the published reference. We report this
because an under-tuned baseline mechanically inflates the apparent
value of anything compared against it: every downstream conclusion in
this paper changed once this fix was in place, a precondition for the
rest of the study rather than an implementation footnote.

\subsection{Implementation}

Sparse retrieval uses BM25 over a SQLite FTS5 index \cite{sqlite-fts5}
rather than a JVM Lucene index, forced by a JVM crash under Pyserini
\cite{pyserini} on our target hardware; two further silent-corruption
risks surfaced at this corpus's scale, in the same category as
Section~\ref{sec:bm25-fix}'s baseline gap and Section~\ref{sec:defect}'s
telemetry defect: FTS5's default MATCH combining operator is
\emph{conjunctive} (collapsing recall without an error), and FTS5
indexes only the \texttt{MATCH} column (an unindexed companion lookup
degrades to a full table scan, an $18\times$ slowdown at $1.5$M rows).
Cross-encoder reranking (\texttt{cross-encoder/ms-marco-MiniLM-L6-v2}
\cite{minilm-cross-encoder}) is applied to the top 100 BM25 candidates,
reranking the top 50. Generation uses a locally hosted, 4-bit quantized
2--3B-parameter model with a hard cap of two calls per query episode and
a 32--64 token structured output, so the language model is never the
entire decision surface, only one typed tool within it.

\subsection{Verifier Calibration Methodology}
\label{sec:calib-method}

Following Section~\ref{sec:protocol}, we collect calibration episodes
(one expansion action per query, true nDCG@10 change against click
labels) on TAIL \emph{validation} ($n=1147$--$1168$ depending on
feature family), and compare three feature families --- (i) six
retrieval-telemetry deltas; (ii) the same six plus four reranker- and
length-derived features; (iii) family (ii) plus three dense-embedding
features --- against three model classes each (fixed-weight baseline,
5-fold CV linear, 5-fold CV GBDT), under Pearson correlation
(Table~\ref{tab:rq1}), to characterize the detection ceiling rather
than accept the first plausible fit. This selects a model and is never
itself reported as evidence the signal generalizes
(Section~\ref{sec:rq1} reports that separately, from one frozen touch
of test). Recovery thresholds are calibrated the same way, by checking
which candidate cutoffs on validation separate true-harmed episodes
from the rest.

\subsection{Metrics}

Retrieval quality is nDCG@10, Recall@100, and MRR, plus the fraction of
queries helped/unchanged/harmed relative to a baseline. For the
recovery study (Section~\ref{sec:rq3}) we report Detection Recall
$P(\text{intervened}\mid\text{harmful})$, False Alarm Rate
$P(\text{intervened}\mid\text{healthy})$, and recovery gain in mean
nDCG@10 with vs.\ without recovery on identically corrupted episodes.
We additionally report a retrospective \emph{oracle ceiling}: per
query, $\max(\text{baseline}, \text{treatment})$ under true click
labels, diagnosing whether headroom exists independent of whether our
qrel-free verifier can find it (Section~\ref{sec:rq2}). Significance is
via paired bootstrap (10{,}000 resamples) throughout.

\subsection{Detection Is Not Actionability}
\label{sec:detect-vs-act}

That action-utility model answers a hard question: given telemetry
before \emph{and} after a specific action, did it help? A logically
prior, cheaper question uses only pre-action telemetry: is unexpanded
retrieval already unhealthy? We build a second model from the same
eight retrieval-telemetry features, labeling a query ``poor'' when
BM25 surfaces zero relevant documents in the top 10 (test prevalence
$0.450$), selected by 5-fold CV on validation and touched once on
frozen test, identically to Section~\ref{sec:calib-method}'s protocol
--- Table~\ref{tab:rq1-test}'s last row.

The gap is large and consistent across val and test: telemetry
genuinely informative about \emph{whether} retrieval is failing
($\text{AUC}=0.649$) is markedly weaker at predicting whether a
\emph{specific candidate action fixes it} ($\text{AUC}=0.552$) ---
both frozen single-touch test numbers from the same features and
protocol, not the same result at different noise levels.
\textbf{RQ1's answer}: qrel-free telemetry reliably detects that
something is wrong, but is only weakly informative about whether a
proposed fix will work --- the gap RQ2's control result and RQ3's
fault-specific pattern trace back to.

\subsection{Is There Any Headroom at All?}
\label{sec:oracle}

opportunity exists, or one exists but this verifier cannot find it. We
resolve this with a retrospective oracle (Section~\ref{sec:setup}): per
query, take whichever of BM25 or the treatment ranking true click
labels say is better --- not deployable, since it uses labels
unavailable at inference time, but useful to bound the second
explanation.

\section{RQ3: Which Failures Are Recoverable?}
\label{sec:rq3}

RQ1 and RQ2 leave open whether observability has \emph{any} practical
value, or whether a weak general detector is simply useless. We test a
narrower claim: that the same weak verifier can still serve as a
safety net against \emph{large, obvious} failures even though it
cannot reliably judge \emph{subtle, natural} ones. We inject three
fault types at their natural point of corruption --- an unsupported
entity appended to the expansion, a grounding passage swapped for a
non-supporting one, and the reranker disabled --- and compare, on
identical corrupted episodes, an always-accept ablation against the
real calibrated controller.

\subsection{A Defect That Changed the Answer}
\label{sec:defect}

An early pass at this study found the reranker-disabled fault
essentially undetectable (recall $0.185$) while the other two looked
strong. Tracing this revealed a real defect: the reranked ranking was
computed, at real latency cost, and fed into telemetry, but never
actually applied to the ranking the agent accepted or evaluated ---
disabling the reranker was mechanically a no-op regardless of verifier
quality. Fixing it exposed a second, entangled defect: the verifier's
telemetry was still computed from the pre-rerank ranking, judging a
different top-$k$ than the one being accepted. We corrected both and
re-ran calibration to confirm the deployed verifier did not need
retraining on the corrected telemetry (corrected-pipeline Pearson
$r=0.146$ vs.\ the original $0.134$). We report this in full because a
component computed purely for observability is architecturally easy to
leave disconnected from the outcome it explains, and the resulting
error looked coherent --- unrealistically strong --- until an
implausible near-zero effect prompted investigation.

The three fault types split into three distinct outcomes, each with a
different explanation, so ``is recovery useful'' has no single answer
--- only a per-failure-type one. \textbf{Entity injection} is
detected almost every time (recall $0.974$) but flagged almost
indiscriminately (false alarm $0.939$): the controller treats nearly
any entity-injected rewrite as suspect whether or not the injection
was actually benign, and rolling back that many healthy episodes
offsets the genuine catches, leaving a positive but not significant
net effect. \textbf{Grounding corruption} is the one clean recovery
success ($+0.0099$, $p<0.05$): moderate recall ($0.528$) paired with a
comparable false alarm rate ($0.469$) is discriminating enough, on
this fault type specifically, to produce a real net gain.
\textbf{Reranker disabled} is never detected at all (recall $0.000$,
false alarm $0.002$): the controller essentially always accepts.

\textbf{Why, causally.} Fitted weights alone
(Section~\ref{sec:calib-method}) show which features the verifier
ignores, not what a fault \emph{does} to its score. We measure this
directly: for each fault, $\Delta x_j = \mathbb{E}[x_j^{\text{fault}} -
x_j^{\text{clean}}]$ per feature $j$, and $\text{Contribution}_j = w_j
\cdot \Delta x_j$ using the frozen verifier's weights ($n{=}79$/fault),
sign relative to its healthy-state direction (Table~\ref{tab:rq3},
last column). Entity injection's dominant feature pushes the score sharply toward
``unhealthy,'' consistent with its high recall; the blunt false-alarm
rate is a threshold problem, not feature-blindness. Grounding
corruption's dominant contribution is an order of magnitude smaller,
matching its near-coin-flip recall. Reranker disabled is
mechanistically distinct: its dominant contribution is large and
\emph{positive}, from \texttt{disagreement} moving in the direction
the verifier reads as improvement --- the fault does not merely evade
weak reranker-derived features (\texttt{reranker\_top\_score}
$+0.0007$), it makes the corrupted state score higher than the clean
one, so the controller is actively misled, not merely blind.

\textbf{RQ3's answer is that recoverability is fault-specific}, and
the attribution shows why: content-level corruption is recoverable
when it perturbs a strongly-weighted feature the unhealthy way
(grounding), a wash when detection is blunt (entity injection), and a
system-level fault is disguised as an improvement when it moves a
strongly-weighted feature the \emph{wrong} way (reranker) --- a
verifier is not uniformly weak or strong across failure types, it can
be actively adversarial to a fault it was never calibrated against.

\label{sec:robustness}

calibration split would not detect without exactly this kind of check.

\section{Discussion}

Read together, RQ1--RQ3, the oracle analysis, and the cross-split
check sketch one finding, not five independent ones.
Section~\ref{sec:detect-vs-act} is load-bearing: the same telemetry
vocabulary detects that retrieval is failing reasonably well (AUC
$0.649$) but is only weakly informative about whether a specific
action will fix it (AUC $0.552$). RQ2 shows the practical consequence
--- a closed control loop built on the weaker signal adds nothing over
a matched static pipeline --- and the oracle and selectivity-frontier
analyses (Section~\ref{sec:oracle}) rule out ``no opportunity exists''
as the explanation: real headroom is available ($+0.0246$ nDCG@10 to a
perfect selector) and the verifier reaches at most $13\%$ of it at any
tested budget. RQ3's causal attribution shows this is not one uniform
weakness but a per-fault property, sharp enough in one case (reranker
disabled) that the verifier actively reads the fault as an
improvement, because it moves a strongly-weighted feature the wrong
way. Section~\ref{sec:robustness} shows the same fragility along a
different axis: the verifier's ranking, held fixed, goes from weakly
informative on TAIL to below-chance on HEAD and TORSO, so whatever
this telemetry captures is tied to the regime it was calibrated on.

Two things here were found only by refusing a convenient result: the
BM25 baseline (Section~\ref{sec:bm25-fix}) looked adequate until
checked against a published reference, reversing RQ2's conclusion; the
reranker-wiring defect (Section~\ref{sec:defect}) looked like a strong
recovery result until one fault type's implausible near-zero effect
prompted investigation. Both are cases where a component is
architecturally easy to leave unchecked against an external reference,
and the resulting error looks coherent rather than broken. A frozen
protocol with a mandatory sanity check (Section~\ref{sec:protocol})
defends against the first; the second we only found by distrusting a
result that seemed too good, which no protocol automates.

\section{Limitations}
\label{sec:limitations}

The oracle ceiling (Section~\ref{sec:oracle}) is retrospective and uses
test-set click labels directly --- a valid upper-bound diagnostic,
never a deployable method. The generator is a locally hosted, quantized
2--3B parameter model under a strict two-call budget; a larger
generator might change RQ1's ceiling or RQ2's null result.
Cross-split robustness (Section~\ref{sec:robustness}) covers
TripClick's three buckets only; other benchmarks remain untested, so
the AUC collapse could be frequency-specific or reflect broader
corpus-shift sensitivity. Click-derived qrels are an imperfect
relevance proxy inherited from the benchmark. The corrected baseline's
title-weight ratio ($10\times$ body) came from a genuine
validation-set plateau, not cherry-picking, but may not transfer
beyond TripClick's title-informative abstracts. The causal attribution
in Section~\ref{sec:rq3} uses the frozen verifier's linear weights as a
local description of its own behavior. A prospective check on one
held-out fault (query-term removal, predicted before running from the
weights alone; \texttt{scripts/12}) got the qualitative direction right
--- detectable, entity-injection-like profile --- but not the specific
dominant feature: the mechanism generalizes qualitatively, not as a
precise single-feature account. The failure-detection model
(Section~\ref{sec:detect-vs-act}) uses one binary definition of ``poor
retrieval''; a graded definition could shift its measured AUC.

\section{Conclusion}

We evaluated a closed-loop, observability-guided query-expansion agent
under a corrected protocol separating model selection from final
evaluation --- surfacing the paper's first finding: an
honestly-selected BM25 fix inverted every downstream conclusion.
Runtime observability reveals retrieval failures reliably (detection
AUC $0.649$), but autonomous recovery needs a stronger property the
same telemetry does not deliver: predicting whether a specific
intervention will help (action-utility AUC $0.552$, below chance
outside its calibration split). That gap, not any single
agent-vs-static comparison, is why the closed-loop agent does not
outperform static expansion and neither outperforms BM25, despite real
headroom the oracle and selectivity-frontier analyses show going
uncaptured. The recovery study shows this is a per-fault,
mechanistically explicable property --- in one case the verifier is
not merely blind to a fault but actively misled by it. We report both
implementation defects found by refusing a convenient result, in the
belief that the discipline to catch them is worth more here than a
flattering number.
